TASK 15 - WEB PORTAL AND PRODUCTION TRADE-OFFS
===============================================
Covers: concept C21 (reliability, latency, cost, security; workflow versus agent versus
multi-agent), and the presentation site with three kinds of login.

Part A - the portal
-------------------
R1  One FastAPI process serves the API and a single-page app (plain JavaScript, no build step).
R2  Three roles with different pages and different agent tools:
      Patient    My report, Ask the assistant, What the assistant can do
      Doctor     Worklist and study view, Sign-off queue, Copilot, Tools and limits
      Employee   Operations, Verification, Architecture, Audit log, Assistant, Tools and limits
R3  Login. Demo accounts; passwords stored as PBKDF2-SHA256 hashes; session in a signed,
    httpOnly, SameSite cookie valid 8 hours; 8 failed attempts per address in 5 minutes locks
    that address out; logins are audited.
R4  The role is read from the server-side user table on every request. Nothing in a request body
    can change role or patient binding.
R5  Every route declares the roles allowed; a refused request returns 403 and is audited.
R6  Agent runs are started as background jobs and polled, so the page shows steps as they
    happen. A run can be read by its owner; staff see other people's runs redacted.
R7  Model output is rendered as text nodes only, never as HTML.
R8  Every answer carries its trace panel; pages show a "research demonstration, not a medical
    device" banner; the login page states what is simulated.
R9  The example dataset is the 10 public LIDC-IDRI studies; three of them have patient accounts.

Part B - when to use what (to be read with the measured numbers in verification/REPORT.md)
-----------------------------------------------------------------------------------------
    Use a workflow (fixed code path) when the steps and their order are known.
        Here: the CT study pipeline. Ten of its eleven nodes are code; the model drafts text at
        one node and is checked. Cheapest, fastest, most reliable, fully testable.
    Use a single agent when the user's question is open and the tool sequence cannot be known in
    advance.
        Here: the three chat assistants. Reliability comes from typed tools, limits, the
        grounding guard, and packaging fixed procedures as skills.
    Use several agents when the work splits into parts that need different context or checking
    by an independent role, and the extra tokens and time are acceptable.
        Here: the assessment brief. Whether it paid off is a measured result of task 08.

    Trade-off      Lever in this system
    Reliability    deterministic categories; schema plus business rules; bounded repair then a
                   template; idempotent writes; checkpoints; human sign-off
    Latency        skills cut model round trips; no model call for normal studies; per-run
                   memoisation of reads; detector result cache
    Cost           token budgets per run; context fitting; local model (no per-token charge,
                   fixed GPU cost)
    Security       scopes and record-level checks in the executor; role checks in HTTP; patient
                   binding in the session; redacted staff traces; audit log; egress guard;
                   approval for writes

Part C - going online
---------------------
The site needs a host that can reach a model. Options, to be chosen by the project owner:
  a. This PC with the local model, exposed through a tunnel. Online only while the PC is on.
  b. A cloud host with a hosted model key (set DWAGENT_PROFILE=cloud and a provider adapter).
     Only the public demo data may be sent to a hosted model.
Chosen: (a). Public mode (python -m dwagent.web.public, DWAGENT_PUBLIC=1) is what the tunnel
points at. Requirements for public mode:
P1  The process refuses to start with the default session secret, or with any account still on
    the password written in the source. The launcher generates a random secret and one random
    password per account into data/runtime/ (not committed); --rotate replaces them.
P2  Passwords are never sent to the browser. The sign-in page lists account names only; the
    project owner hands out passwords.
P3  The portal listens on 127.0.0.1 only. The tunnel program on the same machine is the only
    way in, and it reaches the portal alone: the model server, the retrieval service and the
    DICOM gateway stay unreachable from outside.
P4  Forwarded-address headers are trusted from 127.0.0.1 only, so the login lock-out and the job
    limits count the visitor's address, not the tunnel's.
P5  Admission control on agent jobs (chat, explanation, pipeline): per client (account plus
    address) 2 running and 20 per 10 minutes, 6 running in total; over the limit returns 429 and
    is audited. The demo accounts are shared, so the account alone is not the key.
P6  Response headers: content security policy (scripts from this origin only), no framing,
    no-referrer, nosniff, no-store on API responses, HSTS and noindex in public mode. The session
    cookie is Secure. The interactive API documentation is switched off.
P7  PMC-Patients is licensed for non-commercial use only; the site says it is a research demo.

Verification
------------
Browser run on the local portal (2026-11-18), all three logins:
  doctor    worklist, study view with image and findings, pipeline to sign-off, approve, signed
  patient   signed report and image shown; explanation valid on first attempt; other patient's
            image, worklist, operations, pipeline start and approvals all returned 403
  employee  operations, verification, architecture and audit returned 200; patient report, study
            and worklist returned 403
The measured comparison of workflow, single agent and multi-agent is in verification/REPORT.md
(tasks 03, 05 and 08).
Access model and public mode: tests/test_web.py (15 tests, no model needed) covers the role
matrix, session forgery, login lock-out, job limits, refusal of the default secret and of source
passwords, and that no password reaches the browser. Run against the live public-mode process on
2026-11-19: all three roles signed in with generated passwords, the source passwords were
refused, and every listening port was bound to 127.0.0.1.

Known limits
------------
Demo accounts and an in-memory job table: restarting the server forgets running chat jobs
(pipeline runs survive through their checkpoints). No password reset and no multi-factor login.
The job limits and the login lock-out live in the memory of one process. Visitors share the demo
accounts, so one visitor can sign a report or store an assistant memory that the next one sees.
A public site on this PC is online only while the PC, the model server and the tunnel run.
