DEEPWISE AGENT TOOLS - REQUIREMENTS OVERVIEW
=============================================

Purpose
-------
Role-scoped AI agent tools for a chest CT service, built the way Deepwise deploys its imaging AI:
an AI server inside the hospital network, fed by the CT scanner or PACS, used by doctors, with
results reaching patients, and operated remotely by company engineers. Everything here runs on
public data with a local model. It is a research demonstration, not a medical device.

How to read these files
-----------------------
One file per job task. Each file states the job, the numbered requirements, the code that
implements them, the real data it runs on, and the command that verifies it. Measured results
are never typed into these files: they are written by scripts/verify.py into verification/*.json
and summarised in verification/REPORT.md.

Data (all public, all downloaded by scripts, none committed)
------------------------------------------------------------
LIDC-IDRI subset   10 chest CT studies (1,306 DICOM images, 0.69 GB) from The Cancer Imaging
                   Archive, CC BY 3.0. Chosen from the annotation database so that every branch
                   of the workflow occurs: 2 scans with no annotated nodule, and 2 scans in each
                   size band (< 6, 6-8, 8-15, >= 15 mm). scripts/download_lidc.py
LIDC annotations   The four-reader annotations of all 1,018 LIDC scans (6,859 annotations), from
                   the SQLite file shipped in pylidc (MIT). Used as the reference standard and as
                   the simulated radiologist review.
PMC-Patients       20,400 published patient case summaries (CC BY-NC-SA 4.0, non-commercial),
                   indexed by the earlier project github.com/xiangruiSun/deepwise_rag, which runs
                   unchanged as a sidecar service and is called as a tool.
Not used           INSPECT (Stanford). Data access was not complete, and its licence forbids
                   sending the data to a non-HIPAA API.

Model
-----
qwen3:14b served by Ollama on the local GPU. No patient-like data leaves the machine. The
on-prem profile blocks any outbound call that is not to localhost (config.assert_egress_allowed).

Design rules that apply to every task
-------------------------------------
1. The model never produces a measurement, a category or a diagnosis. Measurements come from
   image analysis, categories from deterministic code (dwagent/ct/lungrads.py), and the model
   writes text that is then checked against both.
2. Authorization is decided from the signed-in principal, never from the prompt or from tool
   arguments. It is enforced in the tool executor on every call and again in the HTTP layer.
3. Anything that writes is idempotent per run. Signing a report needs a human approval.
4. Every model call, tool call, graph node and guard is traced with latency, tokens and errors.
5. A failure is an observation the model can act on, not an exception that ends the run.
6. Verification runs on real data with the real model. Unit tests with a scripted model pin the
   failure-mode behaviour and the domain rules (tests/, 60 tests).

Reference implementations studied for the portal and the access model
---------------------------------------------------------------------
Medplum (open-source FHIR platform)   access policies attached to a membership; a patient policy
                                      parameterised by the patient's own id. Adopted: the patient
                                      binding lives in the principal, not in request data.
Open WebUI, LangGraph Agent Chat UI   tool calls shown as cards in the chat; approval shown as an
                                      inline card with allow and deny; interrupt and resume.
                                      Adopted: trace panel under every answer, sign-off card.
shadcn AI Elements, AG-UI             a tool-call component that follows input, output, error and
                                      waiting-for-approval states. Adopted: step list with status.
Next.js + FastAPI RBAC starters       role and tenant scoping on every query, JWT scoped to the
                                      active role. Adopted: role resolved server-side per request.
Gleamer OS, Avicenna AVI, MONAI Deploy   an orchestration layer between modality, PACS and AI
                                      engines over DICOM. Adopted: a DICOM C-STORE gateway in
                                      front of the pipeline (task 14).
The portal itself is deliberately a no-build single page (plain JavaScript served by FastAPI):
an on-site install inside a hospital has no package registry to pull a front-end build from.
